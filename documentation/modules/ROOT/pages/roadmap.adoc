== Automations

Automations map search results, workflows, and triggers (cron, event bus hook, webhook, etc.) to specific agents for execution.

Existing workflows, such as download systems, will be refactored into the workflow framework. Initial implementation will focus on converting common patterns like YouTube download workflows into reusable Metarr workflows.

Workflows will operate in dry-run mode by default. The system will include a safety mechanism to transition into write mode for testing and production execution.

Metadata management will include a comprehensive scraper system that aggregates information from all available sources.

Once the workflow system is complete, Metarr will support default workflows included on deployment and updated with new versions. These workflows become part of the system's source. The development environment will support workflow testing, allowing developers to paste workflows and have the system perform validation and unit testing.

== Digital Fingerprinting

Metarr will implement media file fingerprinting to serve two purposes: duplicate detection and identifying when files are replaced with different versions (different resolution, codec, etc.). This enables the system to flag when a file is changed and alert users to potential issues.

The system shall consist of two subsystems, an ingest pipeline and a search pipeline, sharing a common fingerprint store. During ingest, each video file shall be processed once to compute and persist a layered set of fingerprints:

* the file size
* a high-speed digital fingerprint (a cryptographic or near-cryptographic hash sampled from the file's bytes) sufficient to detect simple binary duplicates such as renamed but otherwise identical copies
* an audio fingerprint capturing the content of the audio track independent of its container or codec, and a video content fingerprint (perceptual frame hashes and/or scene-cut timing) capable of matching the same underlying movie across differing codecs, framerates, and color depths.

The search pipeline shall evaluate a candidate file against the fingerprint store as a staged cascade, with each stage narrowing the candidate set before the next, more computationally expensive stage runs:

* first filtering by file size,
* then by digital fingerprint to identify exact binary duplicates without further processing,
* then by audio fingerprint to identify same-content files with differing video encodings,
* and finally by video content fingerprint to confirm matches where audio alone is insufficient or absent.

This staged design ensures that inexpensive comparisons eliminate the majority of non-matching candidates before expensive content-based analysis is performed, so that search cost scales with the degree of ambiguity between files rather than with the full cost of content comparison on every candidate.

=== Binary Fingerprinting

Binary fingerprinting enables comparison of two binary files to determine if they are "probably" the same file, regardless of filename. This is used by Metarr for duplicate detection and file identification after renaming.

Fingerprint{Size, Hash} — Hash is SHA-256 over the file's exact size followed by a handful of fixed-size byte windows sampled at evenly spaced offsets (always including the very first and last bytes).

The window count and size are bounded (Config{SampleSize, NumSamples}, default 5 × 1MiB = 5MiB max), so I/O and hashing time stay constant no matter how large the media file is — a 500MB file and a 50GB file fingerprint in roughly the same time.

Since only a few MB are ever hashed regardless of file size, the hash algorithm's own speed becomes negligible — SHA-256 on 5MB is a couple milliseconds, so the package needs zero external dependencies. (The doc comment notes where to swap in BLAKE3/xxhash if broader sample windows are desired.)

Small files (below the sample threshold) fall back to hashing the entire file in one window — still cheap, and avoids edge cases from overlapping windows.

Since the fingerprinting process reads only file content and not filename, path, or mtime, file renames are handled transparently by construction.

This approach is being extended to identify files after transcoding or other transformations, enabling detection of re-encoded media (different codec, resolution, bitrate, etc.).

== Rename

Metarr's rename system will use templates instead of patterns. Users can specify a rename template using Go template, Handlebars, or similar templating languages. Workflows can reference specific templates, and the system will strip special characters and generate valid filenames.

=== Safe Rename

The rename system will include a simulation mode allowing users to preview how different naming conventions would affect their media (workflow simulations). Once a standard naming pattern is established, the system can apply renames and automatically update the correct *arr application to reflect the new paths. If available, Metarr will also update Jellyfin to maintain consistency.

The rename system will support conditional logic, similar to scripting languages. This enables complex rename rules beyond simple regex patterns, potentially using Lua or similar for dynamic renaming decisions.

== Metadata Proxy

A metadata proxy will provide cached and versioned access to all metadata. External systems can point to this proxy to retrieve cached results, with versioning enabled so users can track how documents change over time. This metadata becomes a canonical source alongside native Metarr data.

== Metadata Update

The system will provide automatic updates to external metadata registries when their APIs support it, keeping external systems synchronized with Metarr's data.

== Poster Manager

Metarr's poster manager combines Kometa-like poster creation with a rule system enabling users to switch between different pre-built image packs. Users can create multiple poster and image profiles for each media item, storing them and swapping profiles as needed. Integration with external poster repositories will be crucial to this feature.

Workflows enable sophisticated image pack creation. For example, a workflow can create a Criterion Collection image pack by pulling the source image, applying Criterion branding overlays, adding award indicators, and saving as a pack. Users can apply these packs to their media and easily revert to previous versions if needed. Version control (git-based snapshots and tags) provides an efficient implementation approach.

The key innovation is building the overlay system as a WYSIWYG editor rather than configuration files, making it accessible to non-technical users.

== Metadata Lockdown

Since metadata is the system of record, Metarr will implement a security system that prevents external systems from modifying it using file-level permissions.

This requires several key components:

* Network file permissions must be configured properly. The system requires restrictive permissions; permissive access (777) with unified user credentials defeats the purpose.
* The Metarr agent operates with elevated permissions on the NAS filesystem (uid:100, gid:0 or root).
* External systems (Jellyfin, Radarr, etc.) access the NAS with different, restricted credentials (uid:200, gid:200).
* Role-based access controls (ACLs) define permissions for each system.

The lockdown configuration screen enables administrators to manage access. Groups are created to represent roles, and users/services are assigned to these groups.

Example roles:

* `metarr_nfo_write`: Read/write access for NFO files
* `jellyfin_trickplay`: Create and manage trickplay, read-only on metadata
* `sonarr_create`: Create new items, read-only on metadata
* `external_readonly`: Complete read-only access for external systems

A reset function will restore default permissions to all directories.

=== Open Questions

* How are ACLs applied to files created by external systems (e.g., trickplay)?
* What is the required Windows support approach?

Documentation will include configuration guides and video tutorials for setting up and managing ACLs.

The cleanest pattern for this — and it's a well-worn one, used long before centralized directory services were common — is to treat groups as roles and never put a user's name directly into an ACL. Everything else follows from that one rule.

1. Roles are POSIX groups, one group per (function × permission level), not per person

Don't create role-finance and dump read/write/admin folks all into it. Split by access level so you can grant precisely:

role-finance-ro
role-finance-rw
role-finance-admin
role-hr-ro
role-hr-rw

Users go into these groups as secondary group memberships. A person doing two jobs just belongs to two groups. This is your entire "role assignment" mechanism — /etc/group (or usermod -aG) is the role-assignment database, no LDAP required.

1. Never ACL a username. Always ACL a group.

setfacl -m g:role-finance-rw:rwx /data/finance
setfacl -m g:role-finance-ro:r-x /data/finance

If you ever find yourself typing setfacl -m u:jsmith:..., stop — that's a sign the role model is missing a group, not a reason to special-case a user.

1. Set default ACLs on every directory, not just the current ACL

This is the step people forget, and it's the one that makes the system actually behave like RBAC over time instead of just at setup:

setfacl -d -m g:role-finance-rw:rwx /data/finance
setfacl -d -m g:role-finance-ro:r-x /data/finance

Without -d (default ACL), new files created tomorrow inherit nothing and silently fall back to normal owner/group/other bits. With it, every new file and subdirectory automatically picks up the role grants.

1. Combine with setgid, not in place of it

chmod g+s on directories so new files inherit the group owner, and pair it with a sane base mode and no other access:

chmod 2750 /data/finance
setfacl -m d:o::--- /data/finance   # kill default "other" grant explicitly

Belt-and-suspenders: even if someone strips the ACL, the underlying group ownership still isn't world-readable.

1. Manage the ACL mask deliberately

POSIX ACLs have a mask entry that caps the effective permission of every named group/user entry. setfacl recalculates it automatically most of the time, but when you're debugging "why doesn't this permission take effect," getfacl and check the mask line before anything else — it's the #1 source of "I set the ACL and it didn't work" confusion.

1. Treat the ACL state as code, not as a pile of manual commands

Since you have no central directory to enforce this, drift across machines/directories is the real risk. The clean approach: write the desired state as a small manifest (YAML/JSON — path → group → permission), and a script that applies it idempotently with setfacl and verifies with getfacl -R --absolute-names. Keep that manifest in git. This gets you:

an audit trail of who has access to what and why
a diffable "desired vs actual" check you can cron
no hand-typed one-off ACL commands that nobody remembers six months later

1. If more than one host is involved, solve UID/GID consistency first

POSIX ACLs store numeric UID/GID under the hood. If role-finance-rw is GID 5001 on one box and GID 5002 on another (because groups were created in different orders), your ACLs silently break the moment files move between hosts or go over NFS. Without AD/LDAP, fix this by keeping a static UID/GID allocation table and pushing /etc/group consistently with whatever config management you already have (Ansible/Puppet/Chef, or even a simple synced file + script). This is the part people skip and then debug for hours later.

1. Know the one real limitation: no deny entries

POSIX.1e ACLs are allow-only — there's no explicit "deny" ACE like NFSv4/Windows ACLs have. If you need "everyone in finance except contractors," you can't express that as a deny; you model it by not putting contractors in role-finance-rw and instead giving them a separate, narrower role/group. If that kind of exception logic is common in your org, and you're on a filesystem that supports it (ZFS, or Linux with richacl), NFSv4-style ACLs give you real allow/deny + inheritance flags and are arguably a cleaner fit for RBAC — worth considering if you're not locked into ext4/xfs.

== Agents

The first version of the agents system is done, but it needs to be expanded to make it more usable.

=== Auto Install

Metarr will provide an automated installation and update system:

* Users shell into the target machine and run a Metarr-provided curl command.
* The curl command downloads a script that creates necessary directories, retrieves the agent binary from the server, configures the agent, and starts it as a system service.
** Redis connection information can be encoded in the curl command or provided interactively during the script execution.
* When an agent detects a version mismatch with the server, it automatically downloads and applies updates, maintaining uptime.

Implementation requires a build system that compiles agent binaries and hosts them on a server accessible via curl.  

=== Agent Version Check

Agent binaries will include a build number. When an agent connects to the server, it transmits its version information. The server monitors version mismatches and alerts administrators when agents are out of sync.  

=== Capability Filters

Agents are going to have a list of capabilities, like FFmpeg, FFprobe, and yt-dlp. When the agent starts, it will detect which of those can be run on that host and notify the server if it's possible to run those jobs. That can be used to determine which agent to run a task on.

== UI Task Nodes

Workflows will support interactive UI nodes that render output using templates. These nodes prompt users for input and collect responses. Input types will include text fields, yes/no buttons, and list selections. Response types include:

* Boolean confirmation (ok/cancel)
* String responses
* Rejection/cancellation

== Task Payload Streaming

Some workflows require agents with specialized capabilities (e.g., GPU-only agents) without direct file system access. Metarr will support binary data streaming between server and agents without intermediate file system writes.

When agents process binary data (e.g., FFmpeg thumbnail generation), they produce output streamed directly to the server. The server persists this data to workspace and continues processing, eliminating inefficient intermediate storage.

=== The core pattern

Producer side: hold the data as an io.Reader (whatever is generating or already holding it in memory — a buffer, a pipe from an upstream socket, whatever), open a net.Listener or dial out to the consumer, and io.Copy(conn, reader). Consumer side: io.Copy(destination, conn) where destination is again just an in-memory sink or a forward-on writer. No os.Create, no ioutil.WriteFile, nothing hits the filesystem. io.Copy internally uses a 32KB buffer by default, which is too small for multi-gig transfers — use io.CopyBuffer with a much larger buffer (1–4MB is a reasonable starting point) to cut down on syscall overhead.

=== Putting it together with your event-driven flow

A clean shape: producer publishes a Redis Stream entry (XADD) with transfer metadata (id, size, host:port to dial, maybe a checksum). Consumer, driven by that event, dials the producer directly and starts reading. When the copy finishes, the consumer (or producer) publishes a completion event back through Redis with the checksum/status — small, cheap, and keeps your event-driven architecture intact without ever asking Redis to carry the payload.

If both processes happen to live on the same host, skip the network entirely and use io.Pipe or a shared net.Conn over a Unix domain socket — same code shape, lower overhead than loopback TCP.
