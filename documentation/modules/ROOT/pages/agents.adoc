= Agents

An agent is a small static binary that runs next to your storage and does every
filesystem operation on Metarr's behalf. The server never touches your media
library; it asks an agent to.

== Why the split exists

Walking a large library is I/O-bound, and doing it across a network share is
dramatically slower than doing it locally. Putting a small binary on the machine
that already has the disks mounted turns a network walk into a local one, and
lets the work happen on hardware you have already paid for — a NAS, or a box
with a GPU.

The second reason is containment. The agent holds no database credentials and
*cannot* open a database connection: it is structurally incapable of it, and a
test that walks the real build graph fails the build if that ever stops being
true. See xref:architecture.adoc[Architecture]. A machine sitting on your
storage is a machine you want holding as few secrets as possible.

== Deploying one

Build a static binary for the target platform:

[source,bash]
----
make dist
----

This produces agents for Linux (amd64 and arm64), Windows (amd64) and macOS
(arm64), with cgo disabled so there is nothing to install alongside them. Copy
the one you need onto the machine and run it.

An agent needs exactly two pieces of local configuration — a slug that names it,
and how to reach Redis:

[source,bash]
----
METARR_AGENT_SLUG=nas-01 METARR_REDIS_HOST=10.0.0.5 ./metarr-agent
----

Everything else it needs is published to it by the server. See
xref:configuration.adoc[Configuration] for the full field list.

== How an agent joins

There is no registration endpoint and no handshake. An agent announces itself by
claiming its slug in Redis and then heartbeating:

. It takes a lock on its slug. If a *different* instance already holds that
  lock, the agent refuses to start and tells you to choose another slug. If the
  lock is held by its own previous run — a crash and restart within the timeout —
  it takes it back.
. Every five seconds it writes a presence record containing its identity and
  telemetry, with a fifteen-second expiry. Three missed heartbeats and it
  disappears.
. The server discovers agents by scanning for those presence records.

Because presence is a key with an expiry, an agent that dies simply stops
existing. There is no tombstone to clean up and no stale entry to remove by hand.

A brand-new agent therefore shows up in *System → Agents* as **online but not
configured**. That is the expected steady state until you map libraries to it —
an unconfigured agent receives nothing to do and sits idle.

== Configuring an agent

In *System → Agents*, each agent card shows its status, host, address, the user
it runs as, OS and architecture, version, uptime, and live CPU, memory and GPU
telemetry.

Choose *Configure this agent* to set a display name and, for each scan directory
you have defined, the path by which *that machine* knows it.

[cols="1,1"]
|===
|The server calls it |`nas-01` calls it

|`/mnt/media/movies`
|`D:\Media\Movies`

|`/mnt/media/tv`
|`D:\Media\TV`
|===

Leave a path blank to say "this agent cannot see that library." Records are
always stored under the server's paths, so a library reads the same regardless of
which agent produced it, and you can move a library between agents without
rewriting anything.

An agent's log level is also set here, and applies immediately — no restart. See
xref:logging.adoc[Logging].

== What an agent is told

The server does not send an agent its configuration document. It sends a
deliberately narrow projection, built as an allow-list:

[cols="1,3"]
|===
|Field |Purpose

|Slug, display name
|Identity.

|Parallel count
|How many library items to scan at once.

|Sidecar types
|The classification table, because classification has to happen where the files
are.

|Directories
|Only the ones mapped to *this* agent, and only the agent's own path for each.

|Log level
|Set live from the UI.
|===

Two absences are deliberate. The server's own paths are not included — the agent
has no use for them, and translating back is the server's job. And because the
projection is built by naming permitted fields rather than by removing forbidden
ones, a new setting added to the configuration document does not silently leak:
it has to be named to be sent. The source document holds the administrator's
password hash, every API key, and every Sonarr credential. A test asserts the
projection never carries a secret.

== Mixed platforms

Agents run on Windows, Linux and macOS, and Metarr does not assume they all
match the server.

Path translation infers an agent's operating system from the shape of its root —
a drive letter, a UNC path, or a backslash means Windows — and normalizes
accordingly, with case-insensitive comparison where the filesystem is
case-insensitive. A path that falls outside the agent's mapped root is rejected
rather than passed through.

What can be recorded about a file varies by platform:

[cols="1,1,3"]
|===
|Platform |Ownership and inode |Notes

|Linux
|Yes
|Creation time is left unset — `stat` exposes no birth time, and leaving it
empty keeps "unknown" distinguishable from "created when last written."

|macOS
|Yes
|Full timestamps including creation time.

|Windows and others
|No
|Mode, size, modification time and symlink status only.
|===

== Removing an agent

*Remove agent* deletes its configuration and its stored projection. If the
process is still running it will reappear as online-but-unconfigured on its next
heartbeat — removing an agent from the fleet list is not the same as stopping it.
Stop the process first if you mean to retire it.
